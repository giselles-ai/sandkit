## Letter

Dear future agent,

This session mattered because Sandkit's policy story stopped being a loose sidecar and started becoming a real part of the sandbox lifecycle. The human did not want a generic "network rules" feature. The pressure was to make policy honest in the same way workspace persistence had already been made honest: policy should describe the durable default state of a workspace, per-run overrides should be explicit and temporary, and provider truth should still show through.

The strongest argument in the room was that Vercel Sandbox itself should be the starting point. That ruled out cute rule-list APIs and overly abstract evaluator-first designs. The project moved toward the same three policy modes Vercel exposes: `allow-all`, `deny-all`, and user-defined. From there, the right shape became clear: workspace holds the durable default policy, `workspace.sandbox` remains only a handle, and `runCommand({ policy })` is a one-run override rather than a hidden state mutation.

The next pressure was credentials. We wanted service presets like `codex()` to feel good to use, but not at the cost of leaking secrets into durable state. The settled answer is subtle and important: presets may resolve default credentials at apply time, explicit secrets may be used per run, but durable workspace policy and persisted policy snapshots must never retain raw secret values. Do not casually undo that separation. It is where ergonomics and honesty were made to coexist.

The final theme was evidence. The session kept forcing the code to prove its story: corruption paths, aggregate smoke coverage, real `codex exec` on Vercel Sandbox, and failure messages that reveal the actual broken stage instead of a vague "smoke failed." The system is better now precisely because it stopped pretending a smoke exists unless it really runs.

## Context

- User goal: make workspace policy real, using Vercel Sandbox firewall as the semantic center rather than an abstract network evaluator.
- Project context that mattered:
  - Existing ghost direction already required Sandkit to preserve provider-specific lifecycle truth and keep the public center of gravity at `workspace.sandbox.runCommand(...)`.
  - Sandkit had just gained durable `run` records, policy snapshots, and corruption handling.
  - The user wanted a policy API that feels natural for "prepare broadly, then lock down," while still remaining compatible with future provider abstraction.
  - `sandbox-policy-builder` was added to `opensrc` as a reference for service-first policy authoring and credential brokering.

## Decisions

- Decision: model workspace policy after Vercel Sandbox's three firewall modes.
  - Why: Vercel is the current provider truth, and its `allow-all` / `deny-all` / user-defined model matches the actual semantics Sandkit can honestly promise.
  - Rejected: rule-list APIs like `setPolicy(denyAll(), allowCodex())` because they imply ordered evaluation semantics that do not match the durable policy object Sandkit really stores.
  - Strength: strong.

- Decision: policy source of truth lives on the workspace, not on `workspace.sandbox`.
  - Why: `workspace.sandbox` is a handle, not an independent state owner; policy should survive resume/create and remain part of workspace durability.
  - Rejected: mutable sandbox-handle-owned policy state.
  - Strength: strong.

- Decision: public mutation surface is `workspace.setPolicy(...)`, while temporary override belongs on `workspace.sandbox.runCommand({ ..., policy })`.
  - Why: this preserves the distinction between durable default and one-run override, and keeps the public center of gravity at `workspace.sandbox.runCommand(...)`.
  - Rejected: `workspace.sandbox.updatePolicy(...)` as the main public API, and implicit carry-forward of run-scoped overrides.
  - Strength: strong.

- Decision: use service descriptors plus finished policy builders.
  - Why: `codex()` / `gemini()` / `github()` read as ingredients; `allowService(...)` / `allowServices(...)` read as finished policy values. This kept the language shallower and more stable than `restricted({ services: [...] })`.
  - Rejected: mode/container/leaf mixtures like `restricted({ services: [allowCodex()] })`.
  - Strength: strong.

- Decision: preserve three-mode readability in type names.
  - Why: `WorkspaceUserDefinedPolicy` reads as the third branch of the union better than `WorkspaceAllowServicesPolicy`, which made the mode look like an implementation detail instead of a semantic category.
  - Rejected: leaving the third mode named after service mechanics.
  - Strength: strong.

- Decision: do not preserve fake compatibility for old `network` input.
  - Why: keeping the old option name while silently changing its shape would let callers fall into invalid runtime states and would only hide a real breaking change.
  - Rejected: aliasing `network` to the new policy shape without boundary validation.
  - Strength: strong.

- Decision: wildcard host matching must follow Vercel's semantics exactly.
  - Why: `*.example.com` must match only subdomains, not the parent domain. This was explicitly corrected after review.
  - Rejected: normalization shortcuts that silently broaden wildcard meaning.
  - Strength: strong.

- Decision: default service credentials may exist, but raw secrets must not be persisted.
  - Why: the user wanted `codex()` to "just work" from env, but workspace policy and policy snapshots are durable state. The compromise is: service presets can resolve default credentials at apply time, explicit `apiKey` overrides are allowed, but any secret-bearing policy is rejected for durable workspace storage and redacted before snapshot persistence.
  - Rejected: storing raw `apiKey` values in workspace metadata or policy snapshots; also rejected generic `apiKeyFromEnv` style surface because the user wanted plain `apiKey` and Next.js-style `process.env.X`.
  - Strength: strong.

- Decision: default credential resolution belongs to the service preset side, not a generic `process.env[name]` lookup in the driver.
  - Why: the user explicitly called out Next.js ergonomics and wanted the preset itself to own how its default credential is resolved. The resulting model uses a durable `default` credential kind plus service-specific resolution code.
  - Rejected: keeping env-name strings as the durable source of truth and resolving them generically in the Vercel compiler.
  - Strength: strong in direction, with room for future extension.

- Decision: explicit `apiKey` override attempts must not silently fall back to default credential mode.
  - Why: `codex({ apiKey: undefined })` should fail as an invalid override, not quietly change meaning.
  - Rejected: treating missing explicit values as "same as `codex()`."
  - Strength: strong.

- Decision: codex smoke should be a real Vercel sandbox integration and should separate bootstrap from firewalled execution.
  - Why: the smoke must tell the truth about what failed. Installing `@openai/codex` uses npm registry access and cannot honestly be run under the codex-only policy if the intent is to test codex API brokering.
  - Rejected: running install and execution under the same restricted policy, and treating the smoke as valid if it is not part of aggregate smoke.
  - Strength: strong.

## Guardrails

- Do not reintroduce policy as an evaluator-first or rule-list-first abstraction. The semantic center is Vercel firewall state, not a cute internal rules DSL.
- Do not move policy ownership onto `workspace.sandbox`. It is a handle; workspace remains the durable source of truth.
- Do not let per-run overrides implicitly mutate workspace default policy.
- Do not preserve fake compatibility for removed options like `network`. If compatibility is offered, it must be real and explicit.
- Do not broaden wildcard semantics. `*.example.com` must never match `example.com`.
- Do not store raw secrets in workspace metadata or persisted policy snapshots.
- Do not let explicit `apiKey` overrides silently collapse into default credential mode when values are missing.
- Do not move default credential resolution back into generic driver-side env-name lookup. Service presets own how their default credentials are resolved.
- Do not collapse install/bootstrap and firewalled execution into the same codex smoke phase. That destroys the ability to tell whether the failure is npm/bootstrap-related or codex API/firewall-related.
- Do not treat a skipped smoke as a successful end-to-end verification. The codex smoke is only evidence when the environment is actually present.
