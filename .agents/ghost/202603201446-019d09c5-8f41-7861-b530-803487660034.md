## Letter

Future agent,

Do not treat this codebase as “a wrapper around Vercel Sandbox” and stop there. The real work in this session was about where lifecycle responsibility belongs. The human kept pulling the design back toward the same pressure: callers should see a stable sandbox-shaped interface, while Sandkit owns durability and lifecycle semantics. That pressure was correct.

The most important judgment is this: `workspace.sandbox.runCommand(...)` is the center of the public API, and it represents one unit of work. The provider-specific truth that matters most is that Vercel Sandbox snapshotting is not a passive save. It is a commit that stops the sandbox. We pushed the design until that rule was explicit in both docs and code shape.

Resist any future refactor that makes durability “best effort” in the user layer, or that leaks lifecycle choices like `createOrResumeSandbox()` back into normal app code. If you simplify something, simplify the public surface, not the state semantics.

## Context

- User goal: build Sandkit as a production-grade framework around Vercel Sandbox, inspired by Better Auth, with strong abstractions and minimal lifecycle leakage.
- Project context: repo was bootstrapped from README-only intent; we added a real monorepo layout, a real Vercel smoke app, and then refined the core abstraction around lazy sandbox handles.
- Design pressure that mattered: keep the public API simple while making provider lifecycle rules unavoidable in the implementation.

## Decisions

- Decision: the public API should center on `workspace.sandbox.runCommand(...)`.
  Why: callers should see a sandbox-like interface without manually resolving or resuming provider runtimes.
  Rejected: exposing `createOrResumeSandbox()` as the normal path.
  Strength: strong.

- Decision: `runCommand()` is one unit of work.
  Why: persistence responsibility must stay inside Sandkit; callers should not manually decide when to save state.
  Rejected: leaving persistence to the caller or deferring it to an explicit snapshot step in normal usage.
  Strength: strong.

- Decision: Vercel snapshot semantics must be modeled as commit semantics.
  Why: `snapshot()` stops the sandbox, so it is not just a save helper; it changes lifecycle state.
  Rejected: treating snapshot as a best-effort post-step or swallowing stopped/snapshotting behavior as harmless noise.
  Strength: strong.

- Decision: encode lifecycle in code through types, naming, and transitions.
  Why: the state machine was good as prose, but it would drift unless the code made the same model visible.
  Rejected: relying on comments or docs alone.
  Strength: strong.

- Decision: keep smoke thin and make package code own real adapters/drivers.
  Why: smoke exists to prove concrete execution, not to hold canonical implementations.
  Rejected: leaving `SqliteWorkspaceAdapter` and `VercelSandboxDriver` inline in the smoke app.
  Strength: strong.

## Guardrails

- Do not casually reintroduce `createOrResumeSandbox()` as the normal public path. It is an internal lifecycle primitive.
- Do not move persistence responsibility to callers. If a command mutates state, Sandkit must secure durability as part of the unit of work.
- Do not treat Vercel `snapshot()` as an inert save operation. It stops the sandbox and should be reflected in state transitions.
- Do not collapse lifecycle state back into anonymous metadata blobs without typed transitions. The current direction is toward stronger state modeling, not weaker.
- Do not move the real driver/adapter logic back into `smoke`. Smoke should prove the public API, not contain the authoritative implementation.
