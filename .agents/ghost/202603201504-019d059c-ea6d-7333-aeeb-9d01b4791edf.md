## Letter

This session mattered because the project stopped being an idea in `README.md` and became a real, verified Sandkit skeleton with a working Vercel Sandbox smoke path. The human was not optimizing for a demo that merely looks plausible. The pressure was to make the abstraction honest: if the code claims to manage sandbox lifecycle, then the implementation must survive contact with the real Vercel Sandbox semantics, especially the fact that snapshotting stops the sandbox.

The strongest design argument in the session was that persistence responsibility must belong to Sandkit, not to callers. That pushed the API away from `workspace.createOrResumeSandbox()` as the main user entrypoint and toward `workspace.sandbox.runCommand(...)`, with `runCommand` treated as one unit of work. That in turn forced the internal model to become explicit about lifecycle phases and state transitions. Documentation was useful, but the human repeatedly pushed for a stronger standard: the code itself should reveal the specification.

Future agents should feel this before changing anything: do not flatten sandbox lifecycle into generic “save state” language. For Vercel Sandbox, snapshot is a commit that stops the runtime. The current design is valuable precisely because it stopped lying about that.

## Decisions

- Decision: keep the public API centered on `workspace.sandbox.runCommand(...)`.
  Why: callers should see a stable sandbox-like boundary, not lifecycle plumbing.
  Rejected: making `createOrResumeSandbox()` the primary public path.
  Strength: strong.

- Decision: treat `runCommand` as one unit of work.
  Why: durability must be Sandkit-managed, not caller-managed; this is the minimal boundary that prevents callers from forgetting persistence.
  Rejected: requiring callers to explicitly snapshot or persist after commands.
  Strength: strong.

- Decision: model Vercel Sandbox snapshot semantics honestly.
  Why: `snapshot()` stops the sandbox; pretending it is a passive save creates hidden lifecycle bugs.
  Rejected: “best effort” swallowing of `sandbox_stopped` as if the provider behavior were incidental.
  Strength: strong.

- Decision: default durable commit for `runCommand` is snapshot-based.
  Why: this preserves the state produced by the command without shifting risk to callers.
  Rejected: session-only persistence as the default.
  Strength: strong, but provider-specific tradeoffs may need refinement later.

- Decision: encode lifecycle rules in code structure, not only in docs.
  Why: the human explicitly pushed for a design where naming, types, and transitions make the specification feel inevitable.
  Rejected: relying on prose and comments to explain ad hoc metadata updates.
  Strength: strong.

- Decision: use `lilas` for narrowly-scoped implementation tasks after architecture is clarified.
  Why: parallel execution works well here, but only after the main design pressure is understood.
  Rejected: open-ended delegation with vague prompts.
  Strength: provisional process rule, but it worked well in this session.

## Guardrails

- Do not casually reintroduce `workspace.createOrResumeSandbox()` as the intended public API. It may exist internally, but callers should think in terms of `workspace.sandbox`.

- Do not demote persistence responsibility back to the caller. The project explicitly rejected designs where callers must remember to snapshot or persist after a mutation.

- Do not treat `snapshot()` as a generic save operation. For Vercel Sandbox it is a commit that stops the runtime. Any design that hides this fact behind vague naming is suspect.

- Do not revert the explicit state/commit/transition model back into raw metadata merges. `WorkspaceSandboxState`, `SandboxCommit`, and named transitions are part of the design pressure, not incidental refactoring.

- Do not use broad, vague subagent prompts. When delegating implementation, constrain scope, file ownership, invariants, and validation. `lilas` worked well because the task was tightly framed.

- Do not assume smoke failures are always code failures. This session repeatedly hit environment issues around DNS, sandbox network permissions, stale shell env, and Vercel OIDC tokens. Always separate code regressions from auth/runtime context problems.
