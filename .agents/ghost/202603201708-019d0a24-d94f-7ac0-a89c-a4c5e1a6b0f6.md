Dear future agent,

This session was about turning Sandkit from an internal first-step into something that can honestly be used from the outside without erasing the project’s harder-won semantics. The human kept pushing toward a usable product surface, but the real pressure was not “make README nicer.” It was “make the external story real without lying about lifecycle, persistence, or provider behavior.”

The ghost from earlier in the project was audible the whole time: keep the public center of gravity at `workspace.sandbox.runCommand(...)`, keep persistence inside Sandkit rather than leaking it to callers, and do not flatten Vercel Sandbox snapshots into a fake “save” abstraction. When choices came up, the right answer was usually the one that preserved explicit state/commit semantics even if a simpler shortcut was available.

The other important thread was package honesty. We moved from source-only internals toward a real built package, but we deliberately did not over-generalize. Exports and build entries were trimmed back to what the current smokes actually need. Discovery for `sandkit generate` was added, but only as a convenience layer on top of explicit flags; we did not introduce a `sandkit.config.ts` just to make the CLI feel clever.

- Context
  - The user had already finished the first-step implementation and wanted the next implementation direction, especially around making the Drizzle story real.
  - The near-term personal use case is `drizzle + turso`; a colleague may use `drizzle + postgresql` or raw PostgreSQL.
  - The user strongly preferred avoiding a dedicated `sandkit.config.ts` file unless it carried real weight beyond the initial `generate`.
  - The repo already had a prior ghost emphasizing honest sandbox lifecycle and persistence semantics; this session should be read as extending that direction, not replacing it.

- Decisions
  - Decision: implement a real `drizzleAdapter` before broadening README stories.
    - Why: README examples should correspond to actual package APIs, but the stronger design pressure was preserving the state/commit model while adding real persistence.
    - Rejected: polishing README first without real adapter support.
    - Strength: strong.
  - Decision: canonical generated Drizzle export is `sandkitWorkspaces`, and adapter auto-resolution should target that.
    - Why: this enables `drizzleAdapter(db, { provider: "sqlite" })` when the Drizzle DB is created with generated schema, while still supporting explicit overrides.
    - Rejected: requiring `workspaces` everywhere, or relying on arbitrary table names.
    - Strength: strong.
  - Decision: `drizzleAdapter` may use `db._?.fullSchema` as a convenience fallback, but this is not the core contract.
    - Why: it improves ergonomics now, but we explicitly recognized this as a brittle dependency on Drizzle internals.
    - Rejected: making hidden Drizzle internals the only discovery path, or making `schema` mandatory and breaking the generate-before-runtime flow.
    - Strength: strong in direction, provisional in implementation detail.
  - Decision: `sandkit generate` should use explicit flags first, known-file discovery second, and interactive prompting last.
    - Why: this matches the user’s preference for no extra config file, keeps behavior testable, and avoids over-magic.
    - Rejected: adding `sandkit.config.ts` as a source of truth for first generate.
    - Strength: strong.
  - Decision: current discovery should focus on Drizzle use cases, especially SQLite/Turso and PostgreSQL.
    - Why: these are the real intended use cases. `drizzle.config.*` and `package.json` are enough to support a useful first pass.
    - Rejected: trying to solve raw PostgreSQL/direct SQL discovery now.
    - Strength: strong.
  - Decision: build the package with `tsup`, but keep `exports` and build entries minimal.
    - Why: pack/install verification required a real dist-based package; however, the user explicitly did not want speculative subpath surface area.
    - Rejected: keeping source-only exports; also rejected over-broad `exports` and tsup entries “for future convenience.”
    - Strength: strong.
  - Decision: CLI should be emitted as `dist/bin.js` with a single shebang from source, not from a wrapper or duplicated banner.
    - Why: pack testing exposed a real Node syntax failure caused by duplicate shebang lines.
    - Rejected: keeping a separate `bin/` wrapper, or leaving shebang generation ambiguous.
    - Strength: strong.
  - Decision: split tsup into two explicit configs in one file, and move cleaning to scripts via `del-cli`.
    - Why: the user preferred readability over shared config indirection, and multiple configs with tsup `clean` can delete each other’s outputs.
    - Rejected: shared config object, and tsup-managed clean.
    - Strength: strong.

- Guardrails
  - Do not simplify away the explicit workspace state/commit model just to make persistence adapters or README examples look cleaner.
  - Do not move persistence responsibility back to callers. The value of Sandkit here is that workspace durability remains inside the abstraction.
  - Do not treat `db._?.fullSchema` as a trustworthy long-term contract. It is a convenience fallback, not the semantic center of the Drizzle integration.
  - Do not add `sandkit.config.ts` casually. The user explicitly pushed back on a config file that mostly exists to help first generate.
  - Do not widen package `exports` or tsup entries speculatively. Keep them tied to real smokes and real public API needs.
  - Keep `dist/bin.js` as the actual CLI entry. We already saw a real failure mode from ambiguous shebang handling during pack execution.
  - Discovery should remain subordinate to explicit flags. If heuristics become fancier later, they still should not outrank `--adapter` / `--provider`.

- Next
  - Decide when `packages/sandkit` should stop being `private` and what the minimal publish surface should be before any real release.
  - Add more evidence sources to CLI discovery only if real users need them, likely starting with lightweight DB init file heuristics for Drizzle projects.
  - Consider reducing reliance on Drizzle internals in `drizzleAdapter` once there is a better stable discovery path that does not hurt the generate-before-runtime flow.
  - The next major product step after packaging is still the same as before: runs/policies persistence should catch up to the workspace story so `runCommand()` is a real unit of work, not only a durable workspace shell.
